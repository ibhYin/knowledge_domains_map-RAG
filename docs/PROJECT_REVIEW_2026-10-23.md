# 个人求职 Demo 审查：中文知识图谱 RAG

审查日期：2026-10-23。审查基线：Git `a17f2ed`。面向 AI 应用开发／Python 后端岗位；未提供目标 JD，因此不按算法研究或分布式平台岗位要求评分。

## 结论与使用边界

这是一个**采用图谱检索的中文文档问答原型**：具备文档接入、结构化实体关系抽取、图谱组织、邻域检索、答案生成与可视化的代码闭环。主要价值是能够解释完整的数据流和工程取舍。

目前不能据此宣称“效果优于向量 RAG”“生产级 GraphRAG”或“高精度多跳推理”。当前环境复现了阻断两条抽取链的提示词错误；代码闭环不等于已经验证端到端可用。建议先修复确定性缺陷，再用固定语料完成真实模型演示和对照评测。

本次只新增审查报告和离线检查文件，没有修改产品源码、调用真实模型或修改原有数据。行业比较依据官方文档与官方仓库，属于能力对比，并非在同一语料上的性能排名。

## 1. 实际架构与技术栈

```text
离线：上传 PDF / MD / TXT / DOCX
  → 原始文件落盘 → 文本解析 → 中文标点递归分块 → JSONL 分块
  → 对未处理／内容改变的 chunk 并发调用 LLM
  → Pydantic 实体关系校验 → 字符规范化／别名注册
  → NetworkX MultiDiGraph → graph.json + meta.json

在线：问题
  → LLM 抽取问题中明确出现的实体
  → 规范名／别名／子串定位
  → 双向邻域扩张，按 mention_count + degree 优先保留节点
  → 按边 weight 取前若干关系
  → 实体描述与关系描述拼成上下文 → LLM 非流式生成
  → 返回答案／命中实体／上下文／子图 → JSON 保存问答历史

交付：Vue 3 + Vite + ECharts → FastAPI 静态托管
控制：独立 FastAPI supervisor 管理本机后端子进程
```

| 层次 | 实际实现 | 判断 |
|---|---|---|
| 服务 | Python、FastAPI、Pydantic、Uvicorn | 对个人 Demo 合理；主要问题是状态管理与边界校验 |
| LLM 接入 | LangChain Core／OpenAI 兼容客户端、结构化输出 | 依赖范围克制；无需为了“技术栈丰富”引入 Agent 编排 |
| 图模型 | NetworkX 有向多重图 | 能表达同一实体对之间的多种关系；适合单进程、小语料验证 |
| 存储 | 文档、JSONL、JSON 元数据／历史 | 调试直观；缺少事务、完整快照及任务恢复 |
| 检索 | 实体定位＋有限跳数邻域扩张 | 属于图谱检索增强；没有向量、全文召回或问题相关性重排 |
| 前端 | Vue 3、ECharts、7 个功能页 | 展示完整；目前最有价值的是检索透明度 |
| 本机运行 | Shell、macOS `.command`、双 FastAPI 进程 | 使用方便，但硬编码 Conda 环境影响他人复现 |

## 2. 与行业代表方案比较

以下每种方案解决的侧重点不同，不应把“采用图谱”直接当成比普通 RAG 更先进的证明。

| 对照方案 | 官方方案中的主要能力 | 本项目的位置与差距 | 值得借鉴的最小部分 |
|---|---|---|---|
| 常见混合检索 RAG | 全文／向量召回、合并、排序；Haystack 提供相关检索组件 | 本项目保留实体关系结构，但只能从命名实体切入，且不直接召回原文 | 先补原文全文召回和图谱来源回查，再评估向量召回的收益 |
| Microsoft GraphRAG | Local 结合图谱和原始文本；Global 使用社区报告进行 map-reduce；DRIFT 引入社区信息 | 当前仅有实体邻域扩张，没有社区检测、社区摘要或 Global／DRIFT；也未在回答中补充原文 chunk | 优先借鉴 Local 的图＋原文组织方式；有全局综述需求再做社区摘要 |
| LightRAG | local、global、hybrid、naive、mix；mix 融合图相关检索与文本向量召回 | 当前实现明显更轻，也更容易讲清内部流程，但查询覆盖和检索融合不足 | 借鉴多路召回与统一上下文，保留现有图引擎，不必整体重写 |
| Dify Knowledge Pipeline | 解析／处理流程、全文与向量检索、元数据过滤、重排及引用 | 文档上传和问答并非独有能力；本项目可通过细粒度图谱观察和受控实验展示区别 | 增加检索调试、原文引用、可复现实验，形成自己的问题与结论 |
| RAGFlow | 文档解析、全文与向量索引、任务处理、检索测试及来源展示 | 本项目是轻量文本文档原型，复杂 PDF、扫描件与检索诊断明显欠缺 | 提供 chunk 预览与检索测试，按目标语料决定是否接 OCR／版面解析 |

资料：[Haystack 检索器](https://docs.haystack.deepset.ai/docs/retrievers)、[Microsoft GraphRAG 查询模式](https://microsoft.github.io/graphrag/query/overview/)、[LightRAG 官方仓库](https://github.com/HKUDS/LightRAG)、[Dify Knowledge Pipeline](https://www.dify.ai/blog/introducing-knowledge-pipeline)、[RAGFlow FAQ](https://ragflow.io/docs/dev/faq)、[RAGFlow 检索测试](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/retrieval_testing.md)。以上资料核对于审查当日。

推荐定位：**面向中文关系密集文档、具有检索过程可视化的轻量知识图谱问答系统。**“关系密集”是建议选择的应用场景，当前并没有评测证明其场景优势。

## 3. 项目真正值得保留的亮点

| 亮点 | 代码证据 | 面试时可以讲什么 | 必须保留的边界 |
|---|---|---|---|
| 独立实现索引与查询主流程 | `RagService.ingest/build_graph/answer` | 如何把原始文档转成可检索知识；为什么把存储、抽取、检索分开 | 修复抽取阻断后才能称“完成真实演示验证” |

| 有向多关系图与基础实体规范化 | `MultiDiGraph`、NFKC、大小写／空白规范化、aliases | 为什么用多重有向图；同实体、不同关系如何保留 | 目前是规则别名注册，不能称为完善的跨文档实体消歧 |
| 并发抽取与未变化 chunk 跳过 | `ThreadPoolExecutor`、SHA-256、`processed_chunks` | 模型调用成本如何控制；I/O 型任务为何用线程 | 是同一 chunk 的跳过机制，尚不是完整的增删改增量索引 |
| 可解释的检索展示 | 命中实体、上下文、问答子图、实体浏览与路径展示 | 如何判断问题出在抽取、定位还是扩张 | 展示子图不等于对答案事实进行了证明或逐条引用 |
| 部署依赖较少 | 内存图、文件持久化、前端静态托管 | 为什么个人 Demo 暂时不用图数据库；迁移的触发条件 | 只能描述为小规模本机设计，未测并发容量与内存上限 |

不宜当作核心创新的部分：普通文件上传、FastAPI 接口、聊天气泡、基础 ECharts 展图、可配置模型端点。它们体现完成度，但常见平台已经提供。

## 4. 应在演示前修复的确定性问题

优先级定义：P0 为当前核心流程阻断；P1 为影响演示、数据正确性或调用可信度；P2 为体验及扩展性。没有把个人 Demo 当作必须具备完整企业平台的项目。

### P0：两处抽取提示词都不能正确作为模板构造

位置：[文档抽取链](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/llm/extractor.py:98)、[问题抽取链](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/llm/extractor.py:140)。

两段 system prompt 中包含未转义的 JSON `{...}`，却通过 `("system", prompt_string)` 交给默认 f-string 模板解析。当前 `langchain-core 1.4.0` 在链创建阶段抛出 `ValueError: Invalid format specifier ... Nested replacement fields are not allowed`。两个入口都已离线复现，真实模型尚未被调用。

`extract()` 把这一异常转成 `None`／`[]`。文档抽取失败后建图流程仍最终标为 `done`，问题抽取失败则被表现为无实体命中。因此用户可能把程序错误误判成模型抽取质量问题。

最小修复：两处固定 system 内容均使用现有 LangChain 的 `SystemMessage(content=...)`，保留 human 消息模板；无需手工转义整段 JSON，也无需新依赖。补充“模板构造＋假模型调用”检查。建图状态区分 `done`、`partial`、`error`；抽取错误与真实空结果必须有不同内部状态。

参考：[LangChain ChatPromptTemplate 官方说明](https://reference.langchain.com/python/langchain-core/prompts/chat/ChatPromptTemplate)。

### P1：结构化输出失败后的原始消息恢复分支会再次异常

位置：[EntityExtractor](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/llm/extractor.py:123)、[QueryEntityExtractor](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/llm/extractor.py:163)。

`include_raw=True` 的 `raw` 是 `AIMessage`，当前当字典调用 `.get("content")`。用真实 `AIMessage` 和假 Runnable 已复现 `AttributeError`，且发生在包裹 invoke 的 try 之外。

最小修复：读取消息的 `.content`；确认内容是字符串后再解析。两个调用点都修复，并分别验证可解析 JSON、错误 JSON 和 provider 错误。不要让“恢复分支”把可控失败升级成整批任务失败。

### P1：删除文档后，其事实仍留在图谱并可继续被回答

位置：[删除 API](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/api/routes.py:89)、[文件删除实现](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/pipeline/chunk_store.py:84)。

API 只删注册表、原文和 chunks，未撤销图节点、关系、别名或处理记录。隔离 API 检查中，文档列表已空，而两个实体和关系仍存在。再次“构建图谱”也不会删除没有对应 chunk 的旧事实。

推荐修复：由服务层统一处理文档生命周期。先保存每个 chunk 的结构化抽取结果作为可重放事实；个人 Demo 可在删除后用剩余抽取结果重新合图，避免重新请求 LLM。若之后做精细撤销，必须重新计算来源、权重、描述与别名。只删来源数组而保留来自已删除文档的实体描述，仍会泄漏旧事实。

验收：仅来源于被删文档的事实消失；有其他来源的事实仍保留；重启后结果一致。历史问答是否保留要明确展示为历史快照，不能混同当前知识。

### P1：别名归并结果取决于入库顺序

位置：[别名注册](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/graph/entity_resolver.py:23)、[实体 upsert](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/graph/store.py:55)。

先加入“北大”，再加入别名含“北大”的“北京大学”，得到两个节点；交换顺序只得到一个。`setdefault` 新增了别名映射，却没有把已有节点的属性、边和来源迁移合并。

最小修复：对确定等价的已有节点做真正归并并更新别名指向；测试两个插入顺序及已有边。对同名异义实体，引入类型／领域信息并保留歧义候选，不要把相同字符串一律视为同一对象。

### P1：多个 GraphStore 共享可变默认元数据

位置：[默认元数据与构造](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/graph/store.py:8)、[clear](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/graph/store.py:36)。

浅拷贝 `DEFAULT_META` 没有复制内部的 `processed_chunks`／`stats`。已验证两个新实例的 `processed_chunks` 是同一对象。未从磁盘覆盖这些字段时，状态可串到其他实例或清空后的图，导致错误跳过。

最小修复：使用 `copy.deepcopy(DEFAULT_META)`，或直接构造独立嵌套字典；构造、load 合并默认值和 clear 一并检查。没有必要为了几个默认字段增加新的工厂抽象。

### P1：GraphML 导出不能处理当前图属性，空图也返回空文本

位置：[导出实现](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/graph/persistence.py:34)。

节点／边含 `aliases`、`source_chunks` 等 list 属性，当前直接交给 GraphML，复现 `TypeError: GraphML does not support type <class 'list'>`。另有文本缓冲区问题：在当前环境空图导出长度为 0，并非合法 XML。

最小修复：对导出副本中的非标量属性进行明确序列化，用兼容的字节缓冲或 `generate_graphml` 生成文本，保持原图不变；验证空图和有平行边图的往返解析。MultiDiGraph 本身可以导出，不需要因代码中的误导注释而降成单边图。

### P1：抽取全失败仍报告构建完成

位置：[任务汇总](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/pipeline/service.py:99)。

假模型返回 `None` 时，任务最终为 `done`，仅附带 `failed`。这与 P0 组合后尤其容易掩盖故障。

修复：空待办属于正常完成；待办非空且全部失败属于错误，部分失败明确为部分成功。记录 chunk 级错误类别、失败条数与重试入口。现有客户端已有重试，新增机制应针对最终失败条目，避免无界叠加重试。

### P1：`used_docs` 漏掉仅由节点提供的证据

位置：[来源聚合](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/pipeline/service.py:143)。

回答上下文含节点描述，但来源只从 edges 聚合。单个命中实体没有关系边时，仍能生成回答，`used_docs` 却为空，已通过假模型验证。

最小修复：来源同时覆盖实际进入上下文的节点与边；下一步升级为 chunk 级来源，避免只有不透明的 doc_id。

### P2：种子数量可以突破 `max_nodes`

位置：[扩张入口](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/src/graphrag/graph/store.py:185)。

所有 seeds 在截断前先进入 collected；两个 seeds、`max_nodes=1` 时返回两个节点。真实种子较多或使用 `seed_override` 时，预算名义上有限但没有严格落实。

最小修复：种子去重后明确预算策略，限制或拒绝超额输入；扩张中稳定排序，最终以 token 预算控制上下文。

## 5. 架构、检索与工程方面的不足

本节除特别说明外为代码审查结论或设计风险，没有进行容量压测、浏览器攻击验证或真实模型质量评测。

### 5.1 查询覆盖与证据完整性：最值得投入的改进

**原文被排除在回答上下文之外。** 当前回答仅依赖抽取后的实体／关系描述；原文中的数值、限定条件、否定、版本和不便建模的内容可能丢失。即使 LLM 严格遵守“只依上下文”，也不代表忠实于原文。

改进：沿 `source_chunks` 回查原文，返回 `doc_id + chunk_id + 原文件名 + 页码（若有）+ 原文片段`；为每条答案事实提供可点击引用。先补原文证据，再考虑复杂图算法。

**必须出现图中可定位的实体，召回入口太窄。** “这些方案各有什么限制？”“文档推荐哪些部署方式？”可能没有可用种子，子串＋高频优先也会把模糊实体定位到错误对象。`QueryEntity.type` 虽被抽取，却没有参与定位。

改进：增加基于原文的全文召回和未命中降级。可先用现有环境可用的 SQLite FTS5，但必须明确中文分词／trigram 能力及版本；默认英文式 tokenizer 不是中文检索方案。有条件再补中文 embedding 的语义召回，并用测试集决定是否值得保留。不要在无对照实验时直接承诺向量加入后一定提升。

**邻域排序不理解问题。** 只用出现次数＋图度选节点、用 weight 选边，偏向热门节点；同距离候选没有稳定次序，截断可能丢掉回答必需的低频关系。权重来自 chunk 抽取次数，也不是可信度；重叠分块及重复上传会放大它。

改进：先根据问题、种子及候选原文做简单排序，统一按 chunk 去重；保留种子到证据的关键路径，再评估 RRF／重排。记录每个候选的召回途径与分数。多跳邻域扩张和最短路径展示只是图操作，不能直接写成“实现复杂多跳推理”。

**缺少 token 预算。** 固定 40 个节点／80 条边无法约束描述长度；文档来源堆积也会增长上下文。

改进：对进入模型的实际上下文计 token，明确各类证据预算与截断顺序，记录被丢弃证据数量。用最终上下文评测答案，而非只看子图是否连通。

### 5.2 知识建模与抽取质量

**关系方向未形成严格契约。** Prompt 的例子把“李华 → 星辰科技”标成 `FOUNDED_BY`，与该英文名称的被动含义相反；中文标签又写“创建”。

改进：保留 `FOUNDED_BY` 时统一为“组织 → 创始人”，或明确改成主动关系并同步 Schema、提示词、存储、前端映射和样例。先做少量带方向的金标准三元组。不要只改一个中文标签而保留语义矛盾。

**相对时间被要求强制改成具体年份，但没传入文档时间。** 系统不知道原文写于何时，要求模型把“去年”转成年份会诱发猜测。

改进：有 publication_date 时才规范化；缺失时保留原始表述并标记时间未决。不要使用上传年份替代发表年份。

**描述合并用“更长的覆盖”，关系描述保留首次值。** 长描述不一定更正确；跨文档冲突、时期变化、否定事实与多个事件没有单独表示。同名实体又仅依字符串主键合并。

改进：保留 chunk 级抽取记录与来源，先暴露冲突而非覆盖；按目标领域补最必要的类型／关系／时间字段。没有必要立即建设通用本体平台或对所有实体做模型消歧。

**分块合理但偏基础。** 中文标点递归切分适合作为基线；固定字符长度、逐页 PDF 读取会切断跨页语义，DOCX 表格行拼接缺表头语义。扫描 PDF 无文本时被静默跳过，可能上传成功但零 chunk。

改进：先补 chunk 预览、零有效文本的明确提示、标题路径和表头保留。目标材料确实包含扫描件再接 OCR／版面解析；不必为了演示范围主动扩成多模态平台。

### 5.3 索引生命周期、并发和持久化

**现有增量机制仅比较 chunk 内容哈希。** 同一文件重复上传按文件名＋时间产生新 ID，因此不去重；模型、提示词、Schema 或分块配置变更也不会使已有抽取结果自动失效。

改进：文档内容 hash 负责去重，chunk 内容 hash 与抽取版本指纹共同定义可复用结果；指纹包含 model、prompt/schema 版本及相关配置。缓存结构化抽取结果，支持重新合图。对文档更新撤销旧版本的事实，避免追加后留下旧关系。

**任务没有全生命周期互斥。** 每次构建请求起一个 daemon 线程；现有 `_lock` 只保护单次图写入，未覆盖待办计算、processed 更新、clear、delete 和 save。两个构建任务可能重复抽取和累计权重，clear 与构建交错也可能重新写回事实。

改进：个人 Demo 先采用“同一时刻一个构建任务”，重复请求返回正在运行的 job；clear／delete 与构建统一管理写入。查询读取稳定快照，避免在线看到半建成图。无需为此直接引入 Celery＋Redis；真的需要跨进程恢复和排队后再升级。

**JSON 全量写入缺少原子性，graph 和 meta 又分开保存。** 进程退出或写入异常可能留下半截文件／不匹配版本；问答历史和文档注册表也有读改写竞争。

改进：最小方案为临时文件＋原子替换，图与元数据采用同一个版本快照并保留最近成功版本。若需要事务化文档、chunk、任务与来源管理，优先考虑标准库 SQLite；NetworkX 可继续做内存检索。仅当规模、并发或查询需求实测触顶，再迁移持久化图数据库。

**任务状态仅在进程内，重启丢失；多 Uvicorn worker 各有独立图和 jobs。** 当前部署应明确单 worker，不应直接加 worker 数假装提高吞吐。哈希只在整批结束时持久化，长任务被中断可能再次付出抽取成本。

改进：记录任务及 chunk 完成状态，启动后对中断任务标记可恢复；先让恢复语义正确，再决定是否需要后台 worker 服务。

### 5.4 接口与安全边界

**无鉴权的配置、清图和进程控制 API 与普通问答共用。** 两个服务默认绑定 loopback 降低了本机演示的暴露面，但不能因此把它们直接部署为公开服务。主 API CORS 为 `*`，配置允许更改模型请求端点，敏感值没有字段长度／换行校验。

改进：本机默认保持 loopback，明确允许的 Origin；若公开演示，优先提供只读固定语料版本，关闭设置／上传／清图／进程控制入口。确需管理入口再加简单鉴权。校验 URL、长度与换行，安全序列化环境配置；不要对任意端点发送已有密钥。

**图谱 tooltip 把上传文本衍生的名称与描述拼成 HTML。** 见 [GraphViz.vue](/Volumes/xiaoPai/Documents/RAG+Konwledge_domains_map/web/src/components/GraphViz.vue:59)。该位置没有 HTML 转义，属于不可信内容进入 HTML 的风险路径；本次没有做浏览器执行验证，不能宣称已经完成 XSS 利用证明。

改进：对动态值转义或改用安全文本渲染；不要把模型输出当成可信内容。文档内容进入抽取／回答时也要明确是证据数据，加入提示注入样例，结合引用与评测检查行为。

**上传没有大小／数量限制，解析在 async 路由中直接同步执行。** 路由先把文件全部读入内存，再同步解析 PDF／DOCX，会占用事件循环。问题与实体名也缺少长度／非空约束，结构化输出校验并不能替代事实校验。

改进：限制上传数量、单文件与总大小、问题长度；对解析错误和零文本返回明确状态，清理未成功登记的文件；将同步解析放入线程池或后续后台任务。该事件循环问题针对上传入口，其他 `def` 路由由框架在线程池执行，不能泛化成“全后端都在阻塞事件循环”。

### 5.5 配置、运行和前端体验

**LLM 热更新不完整。** `GraphSearch` 缓存 `QueryEntityExtractor`，后者缓存 LLM／chain；问答生成每次新建客户端。因此提示词问题修好后，修改模型可能出现“新模型回答、旧模型识别实体”。抽取期间逐 chunk 读取配置也可能让一次任务混用模型。

改进：每个任务／请求使用同一份配置快照；配置变化时使缓存失效。任务记录模型和抽取指纹。两处 `write_env` 实现应复用已有配置模块，避免双份维护。

**supervisor 自控制增加复杂度。** 前端通过将要被停止的后端转发 stop／restart 请求；代理超时为 5 秒，控制服务启动可等待 90 秒。开发模式没有自动启动 supervisor，控制页可能不可用；manager 只认识自己启动的进程。

改进：把本机运维从主要求职亮点中降级。保留终端启动／停止即可；若保留控制台，使其状态与运维入口独立于被控进程并统一超时。没有必要把它包装成微服务或进程编排平台。

**他人首次复现不顺畅。** README 假定已有 `langchain` Conda 环境，只补装两个包；没有覆盖空环境安装、`npm ci` 与生产前端构建。启动脚本固定 `conda activate langchain`，Python 依赖未锁定，NetworkX 的最低版本声明未与实际使用的 API 做兼容验证。

改进：给出从干净环境到可演示的完整命令、Python／Node 版本与依赖锁定结果；提供无密钥的离线样例和明确的真实模型配置步骤。先写好标准 venv 流程；Docker 只作为减少评审环境差异的可选交付方式。

**前端存在可直接影响演示的问题。** 代码审查发现：路径请求失败时 `pathResult=null`，但错误文字位于 `v-if="pathResult"` 内，错误不会显示；路径输入是名称，后端直接按 key 查找，未复用 `locate`；Graph 页轮询缺少卸载清理，后续轮询错误可能变成未处理拒绝。图中边 tooltip 字段为字符串，顶层 formatter 却按函数调用，也存在类型不一致。

改进：错误展示与成功结果解耦，名称定位在服务端统一处理；明确有向路径与任意关联路径的区别；清理轮询并处理失败。主要交互控件使用可键盘操作的 button／链接和显式 label。以上 UI 结论来自源码，未做浏览器逐页交互验收。

**聊天界面没有多轮上下文，也没有流式输出。** 请求只传当前 question；历史只是存档，不是会话记忆。不要写“支持多轮对话”。如果目标场景需要追问，先做指代消解并限定保留的上下文；流式输出属于体验提升，不能提高检索正确性。

**全量展图与整包 ECharts 增大前端负担。** 当前 `/graph/viz` 全量返回图，force 布局显示所有边标签；生产构建输出单个 JS 为 1,216.77 kB，gzip 409.47 kB，并有体积警告。

改进：先按 ECharts 模块实际需要导入、页面按需加载；大图默认搜索实体／局部展开，限制节点并按需显示标签。具体节点规模上限应实测，不能在简历里填写未经压测的容量。

## 7. 最有简历价值的评测方案

建议起步构建 **60 道人工核对的问题**，这是未来实验计划，不是本项目已有成绩。

| 类别 | 建议题数 | 检查目的 |
|---|---:|---|
| 单跳事实 | 15 | 基本事实与引用是否正确 |
| 跨文档两跳关系 | 15 | 图谱结构是否带来可测收益 |
| 别名、同义问法、无明确实体的问法 | 10 | 定位与召回覆盖 |
| 版本、时间、否定和冲突 | 10 | 图抽取的有损压缩与事实更新 |
| 资料中无答案 | 10 | 正确拒答，避免无依据生成 |

可将 20 道用于调参、40 道作为冻结测试集；若语料或样本相关性很强，按文档主题分组划分，避免近重复泄漏。数据过小时报告逐题结果，不能只给一个看似稳定的百分比。

比较配置：A 全文检索；B 文本向量检索；C 纯图谱检索；D 图谱＋原文检索；可选 E 在 D 上加入重排。保持原始语料、生成模型、尽可能一致的分块与上下文预算；需要不同索引方式时明确差异。记录索引成本；固定查询集；不要把更大的上下文预算当作算法本身的提升。

优先指标：支持证据 Recall@k／MRR（有标注 chunk 时）、人工事实正确率、引用支持率、无答案题的正确拒答率及可回答题的误拒答率、端到端 P50/P95、每次问题 token／费用、索引调用次数与失败率。Faithfulness 之外还要核对原文事实，因为“忠实复述抽错的图”仍可能错。

可采用 Ragas 的 Context Precision／Recall、Faithfulness、Response Relevancy 辅助评价，但模型裁判结果应抽样人工复核，不能当作唯一真值。参考：[Ragas 官方指标列表](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)。

建议保留实验字段：`question_id, case_type, corpus_version, index_version, retriever, model, context_budget, evidence_chunk_ids, answer, citations, correctness, refusal_result, retrieval_ms, generation_ms, input_tokens, output_tokens, error`。记录成功样本的同时统计调用失败，否则性能数字会偏乐观。

## 9. 面试中最应准备的回答

1. **为什么自己实现而不直接使用 LightRAG／Dify？** 为了验证特定领域关系检索和可解释流程，控制抽取、图构建、检索与评测；通用文档平台本身已有成熟方案，生产落地需权衡复用成本。
2. **为什么暂时使用 NetworkX？** 个人 Demo 的目标是验证正确性和检索价值，单机内存图容易调试；会以图规模、内存、更新延迟与并发一致性实测决定迁移，而非声称它适合所有规模。
3. **图比向量好在哪里？** 对显式关系、跨文档连接有结构优势的可能；对无实体语义问题与原文细节可能更差。最终回答必须结合本项目实验，而非套用论文成绩。
4. **如何避免幻觉？** Schema 只约束形状；需要原文证据、引用、无答案检测、抽取错误处理及独立评测。图中的事实本身也是模型产物，不能视为绝对真值。
5. **最难的工程问题是什么？** 可以围绕已复现的别名顺序依赖、删除一致性、配置缓存或失败被当成功展开，讲清根因、最小修复与验证方式。
