# 建图速度、进度显示与检查点修复

日期：2026-10-24。适用场景：个人求职 Demo、单机小规模图谱；不引入队列、数据库或额外后台服务。

## 查到的事实

- 当前真实任务为 1,823 个分块，抽取并发为 4。每个分块单独调用模型，不能把它当作一次普通问答。
- 20:31 检查时进度为 720 / 1,823、失败 21；当时日志显示 19 次 APITimeoutError、2 次输出解析失败，没有旧模板错误。
- 客户端单次超时为 120 秒、最多重试 3 次；超时分块会占用较长时间。日志没有逐请求耗时，不能给出可靠完成时间或精确归因比例。
- 原代码按 futures 的提交顺序收结果，前面的慢请求会阻塞后面已完成结果的进度统计；这影响可见进度，不代表切换为 as_completed 就能让模型本身更快。
- 原任务 ID 只保存在启动它的浏览器中，其他浏览器／未记录该 ID 的页面不能自行发现任务；之前的切页修复没有完全覆盖这个场景。
- 整批结束才发布图谱，使长任务一直显示 0 个节点／关系。当前运行中的旧进程仍采用这个逻辑。

## 已发布到网页的修复

1. 显示醒目的百分比、成功／失败数、最近获取进度的时间。切到其他页面，顶部仍保留任务入口。
2. 从后端发现当前任务；保留本地 ID 和任务链接作为辅助恢复方式。
3. 构建中没有发布结果时显示“等待发布”和明确说明，避免误导为没有上传文档。
4. 为避免重启导致当前任务的未保存结果丢失，仅在本次构建产物 index.html 中附加经过后端状态确认的任务 ID。业务源码不硬编码具体任务 ID；正常源码 index.html 不包含此运行时信息。新版后端启动后优先使用 `/api/graph/build/current`，常规重新构建前端会清除这条一次性发布信息。

## 后端改进：已实现并通过检查，当前旧任务未中途加载

- 增加当前任务查询接口；已有 running 任务时重复提交返回该任务 ID，避免重复模型调用。
- 使用标准库 as_completed，谁完成先处理谁，并返回暂存图的节点／关系计数。
- 首个成功分块立即保存；之后默认每 50 个已处理分块保存一次。复制稳定快照后发布，继续合图不会修改已发布快照。
- graph.json 同时保存图数据和成功处理记录，使用同目录临时文件、flush／fsync、os.replace 原子提交；仍兼容旧图＋meta.json 格式。meta.json 作为兼容镜像，镜像写失败不会使已提交的图谱失效。
- 后续异常或进程中断后保留最近检查点；重新构建跳过已保存成功分块。尚未保存的批次仍可能需要重做，不声称事务覆盖整批任务或跨进程自动续跑。
- 新增可选 EXTRACTION_THINKING=disabled，仅在抽取客户端设置 thinking；回答客户端不发送此选项，默认未配置时所有客户端均不额外发送。只对已确认支持该参数的模型使用。

为了不丢掉当前旧任务的未保存结果，没有重启后端。后端 PID 保持 7027。上述后端功能及新抽取参数需要当前任务完成保存、服务重新启动后才生效；本轮任务的实际吞吐没有因为修改磁盘源码而自动提升。
